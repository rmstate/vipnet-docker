# Routing and connectivity

This guide explains how to inspect the route to a protected resource and troubleshoot the forward and return paths.

## Inspect the client network

After the client has started and its configuration has been applied, run:

```bash
sudo docker exec CONTAINER_NAME vipnetclient info
sudo docker exec CONTAINER_NAME ip -br addr
sudo docker exec CONTAINER_NAME ip route
```

Replace `CONTAINER_NAME` with the actual container name. The host and container have separate network namespaces, so their interfaces and routes may differ.

## Check the route to a target

Choose the IP address of a resource you are authorized to test. Then inspect routing both inside the container and on the host:

```bash
sudo docker exec CONTAINER_NAME ip route get TARGET_IP
ip route
ip route get TARGET_IP
```

Replace `TARGET_IP` with the target's IPv4 address. Do not type placeholder values literally.

The example addresses `198.51.100.117` and `192.0.2.120` are documentation-only addresses reserved for examples; they are not real VPN endpoints or targets.

Save the current routing-table output before changing routes. Add only the route required for the intended test and verify that it uses the expected next hop and interface.

## Verify the forward and return paths

For a TCP connection, check each stage:

1. Does the host route the destination to the expected next hop?
2. Does the packet enter the container on the expected interface?
3. Does it leave through the VPN tunnel?
4. Does the destination or a downstream device return a SYN-ACK?
5. Does the response return through the expected path?

If the connection fails, inspect the routes, forwarding state, firewall rules, NAT rules, and packet captures on the relevant interfaces. A missing SYN-ACK may be caused by the destination or an intermediate network, not necessarily by ViPNet.

For an authorized test, `tcpdump` can help compare packets on the host and inside the container. Review captures before sharing them; they may contain internal addresses or sensitive traffic.

## Routing traffic from other machines

Forwarding traffic from other hosts is a separate setup from routing traffic generated by the Docker host itself. Depending on the topology, it may require host routes, IP forwarding, firewall rules, and NAT. Apply only the rules required by your design; do not disable the firewall globally or use `--privileged` as a general troubleshooting shortcut.

See [Troubleshooting](04-troubleshooting.md) for common failure modes.
